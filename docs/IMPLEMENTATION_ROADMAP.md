## 1. Document and dependency review

Sources: the original assignment, the earlier requirements analysis, the reviewed PRD/HLD/LLD, requirement traceability, design review, and the user's latest instructions. The latest direct request limits this deliverable to the complete overview plus Phase 1 details/prompt; it overrides the attachment's request for detailed prompts for every phase. Earlier analysis suggestions about account ownership, goal history, and partial updates are superseded by the approved single-user design, current-only goals, and full PUT meal updates. The reviewed documents resolve these choices; this roadmap does not reopen them.

The manual browser-to-database workflow must pass before AI integration. Therefore frontend foundation and manual UI occur before AI, as expressly required by the attachment's special ordering rule. Missing external access must be reported as a verification blocker, never replaced with fabricated success.

Dependencies below are technical prerequisites. The intended execution remains Phase 1 through Phase 12, one verified phase at a time. Phase 5 is small but intentional: its persisted goal contract needs to be stable before the combined manual interface and goal-comparison work.

## 3. Fixed constraints throughout implementation

- Strict TypeScript ES modules/TSX; Node 24, Express 5, React/Vite/React Router; backend production executes emitted JavaScript with Node; Recharts and useful React Hook Form/Zod when their feature is implemented. Exact compatible dependency versions are selected and locked during implementation.
- Aiven PostgreSQL through backend-only pg, one shared pool per process, parameterized queries, explicit SQL migrations and same-client transactions with finally-release. Verify TLS against the Aiven CA; never disable verification.
- Mandatory single user, persisted singleton profile, current-only goals, no accounts/auth/ownership fields. Multi-user, chat and PDF import remain separate bonuses after the mandatory audit.
- Consumption DATE is separate from timestamps. Asia/Kolkata is the initial persisted timezone; the backend derives today. Reject future consumption on create/update; inclusive queries may display future days. Weeks are Monday–Sunday.
- Saved nutrients are consumed totals. Full PUT replaces writable meal fields. Changing quantity does not implicitly multiply nutrition. Preserve unknown micronutrients as NULL and known zero as zero.
- History and report-bucket paging use page 1 / page_size 20 defaults and maximum 100. Reports aggregate the entire matching dataset; their page changes only returned buckets. Report ranges have a 366-inclusive-day bound.
- Goal comparisons use current targets and the same elapsed selected dates; identify that basis on historical charts. Do not divide by zero/unset targets or invent actual weight.
- Six micros: sodium_mg, calcium_mg, iron_mg, potassium_mg, vitamin_c_mg and vitamin_d_mcg. Preserve their separate units and completeness counts.
- AI accepts JPEG/PNG/WebP up to 10,000,000 file bytes. Normalize validated images to bounded JPEG for provider interoperability. Gemini first; Grok at most once only for eligible transport/output failures. Validate every provider output. Extraction has no persistence dependency and never saves a meal.
- Preserve LLD limits: 25-second provider attempt, 55-second handler after upload, 60-second frontend timeout, bounded decode/normalization, rate/concurrency limits and true cancellation. Manual functionality does not require AI credentials.
- No Redis, queue, ORM, microservices, global state framework, generic CRUD framework or speculative abstractions. Add dependencies only for a current responsibility. Comments explain non-obvious rules and decisions; names and functions should remain easy to explain.

## 4. Verification and progression policy

Every phase follows **IMPLEMENT → RUN → TEST → VERIFY → FIX → RE-TEST → REPORT**. Implementation alone does not pass a phase. Tests exercise behavior and meaningful failure cases, rather than merely repeating implementation details. Previous relevant gates remain intact; broaden checks when a change creates a concrete cross-feature risk.

Each handoff records changed files, commands with expected/actual outcomes, automated test counts, manual checks, problems/fixes, deviations and unresolved blockers. An unavailable browser, database, provider or install environment is stated explicitly and is not a passed check. Do not silently skip a required gate.

Security, documentation and comments are implemented alongside the feature that needs them. Phase 11 verifies the assembled behavior; it is not the first time validation/security are added. Phase 12 separately challenges the submission claims and the documented setup. Its requirement matrix must distinguish complete functionality from partial implementations and inaccessible verification.

README grows with each phase. By Phase 12 it covers overview, stack, prerequisites, versions, environment variables, Aiven/CA, migrations, separate startup, AI configuration, tests, production build, synthetic example, assumptions, limitations and single-user deployment implications.

Bonus work is not numbered into this mandatory sequence and has no mandatory dependants. Authentication/private ownership, conversational actions and PDF bulk import each need a separate reviewed scope after the mandatory application passes.

Only Phase 1 is specified for implementation now. After its result and repository state are provided, prepare Phase 2 using that actual state; do not generate or execute its coding prompt in this deliverable.
